# Contributing to GeneralsX

Thank you for helping. This page explains how a change gets from a pull request into a release.

## How this repository works

This repository holds the source of each published release. Development happens in a separate repository, and every
release adds one snapshot commit here. A pull request is therefore not merged as it is:

1. You open a pull request against `main`. Automatic checks run on it once the maintainer approves the run (every
   run from outside the project waits for that approval).
2. The maintainer reviews it. Changes may be requested.
3. Once approved, the change is applied in development with you as its author, and goes through the same tests as
   every other change on all supported platforms.
4. It ships in the next release. The pull request is then closed or merged with a link to that release.

For anything bigger than a small fix, open an issue first and describe what you want to change, so no one spends
time on work that cannot be taken.

## Building

You need your own copy of *Command & Conquer: Generals — Zero Hour* to run the game; no game files are in this
repository.

| Platform | Preset | Guide |
|---|---|---|
| Windows x64 | `win64` | `CMakePresets.json`, `scripts/build/windows/` |
| Linux x86_64 | `linux64-deploy` | [docs/BUILD/LINUX.md](docs/BUILD/LINUX.md) |
| macOS (Apple silicon) | `macos-vulkan` | [docs/BUILD/MACOS.md](docs/BUILD/MACOS.md) |
| iOS / iPadOS (testing) | `ios-vulkan` | [docs/BUILD/IOS.md](docs/BUILD/IOS.md) |

The Apple builds need the DXVK submodule: `git submodule update --init --recursive references/fbraz3-dxvk`.
[SOURCE.md](SOURCE.md) has more detail.

## Simulation code

Matches run in lockstep: every player's game must compute exactly the same result. A change to the simulation
(anything under `GameLogic`, `Common` or `GameNetwork`, and the math libraries) must:

* give the same result on x64 and arm64 and with every supported compiler;
* not depend on uninitialised memory, pointer values, unordered container order, wall-clock time or threads;
* say in the pull request that it touches the simulation.

A build with such a change has a different source id and does not join players on the released version. That is
expected; the maintainer runs the cross-platform checks before it ships.

## Style

* Match the code around your change: naming, braces, indentation (see `.editorconfig`).
* Comments are short and factual. Say why the code does something, not the story of how it was written.
* No tool or assistant signatures in code, comments or commit messages ("generated by …", co-author lines for
  tools), no chat transcripts or logs, no personal names, addresses, host names or IP addresses.
* You may use any tools you like, but you are the author: understand every line you submit, and test it.
* One topic per pull request, with a title that says what it changes.

## What cannot be accepted

* Files from the retail game or anything extracted from them: art, audio, video, maps, INI or script data, `.big`
  archives. They belong to Electronic Arts.
* Binary files of any kind, images included. Build inputs must be source. Show screenshots in the pull request
  description; if a change needs an image file, the maintainer adds it.
* Code you do not have the right to publish under the GPL-3.0-or-later.
* Generated files without the generator that produces them.

The signature code in `GXEd25519`, `GXSha512` and `GXIdentityAssertion` is also built into the GeneralsX updater, which

## Reporting bugs and security problems

* Bugs and crashes: open an issue with the bug report form.
* Security problems: never in public. See [SECURITY.md](SECURITY.md).
