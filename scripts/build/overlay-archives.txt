# The community-patch overlay set: the archives that must reach EVERY peer.
#
# GeneralsX:
#
# One filename per line, blank lines and '#' comments ignored. This file is the single
# definition of the set, read by every packaging and deploy script, so the four platforms
# cannot drift. Add a line here and it ships everywhere; do not name an archive anywhere else.
#
# WHAT EARNS A PLACE ON THIS LIST, and it is not "we like this mod". An archive belongs here
# only if removing it MOVES dataID, because dataID is what peers refuse each other over
# (SimIdCompare: engineID, sourceID, dataID, ordinalID - assetID and parseID are warnings).
# Everything else is a local preference and must stay off the list, or every friend downloads
# it for nothing.
#
# MEASURED 2026-08-12, leave-one-out over the six non-retail archives the fleet carries, each
# arm read from the engine's own '[SIMID] local' line (evidence:
# docs/WORKDIR/evidence/patch-overlay-wiring-2026-08-12.md):
#
#   fleet, all six mounted                       data=FA018128   <- the value to preserve
#   minus !HotkeysLeikezeIndicatorsZH.big        data=9F59E16C   MOVED -> load-bearing
#   minus 500_900_CommunityPatch_CoreINI.big     data=ED47F3AA   MOVED -> load-bearing
#   minus !HotkeysLeikezeZH.big                  data=FA018128   unchanged
#   minus 340_ControlBarPro-Fix1440ZH.big        data=FA018128   unchanged
#   minus 340_ControlBarPro1440ZH.big            data=FA018128   unchanged
#   minus 340_ControlBarProZH.big                data=FA018128   unchanged
#
# and the confirming arm, because leave-one-out only clears each archive one at a time:
#
#   retail + these two ALONE, nothing else       data=FA018128   <- a friend joins the fleet
#
# So the owner keeps four cosmetic archives no friend ever downloads, and the join is still
# legal. The friend's client will post one chat line - "the other machine has a different set
# of game archives loaded (mods?)" - because assetID does differ. That warning is accurate and
# is not a denial; the archives behind it are proven not to touch dataID.
#
# WHY THE HOTKEYS ARCHIVE IS ON A LIST ABOUT A PATCH. It overrides Data\INI\CommandButton.ini,
# which ControlBar::init loads with a nullptr Xfer - so its bytes never reach m_iniCRC and are
# covered instead by the looseID allow-list (SimulationId.cpp, TheSuperHackers#80). The
# fingerprint hashes bytes, not meaning: a hotkey-only edit is still a different file. It is 28
# MB of the 29 MB this list costs a friend, and dropping it from the fleet is the one lever that
# makes the download ~1 MB - the owner's call, not a script's.
#
# REMOVING A LINE IS NOT A ONE-LINE CHANGE, and this is the sharpest edge in the whole design.
# Nothing deletes: migrate-patch-overlay.sh iterates the CURRENT entries, and on Windows the
# launcher's place_tree() only ever copies what the payload staged (gxlaunch.c:1831). So an
# archive dropped from this list stays on every install that already has it - the engine mounts
# every .big in the overlay directory - and those peers keep the OLD dataID while fresh installs
# compute the new one. The fleet splits in two, silently, and each half reads the other as a
# network problem.
#
# Until the launcher can prune, which it cannot today, removing an entry means: edit this file,
# AND sweep GeneralsXPatch on every install that already exists. gx_overlay_where reports a stale
# archive as UNEXPECTED, which is what makes the split visible rather than silent - but only on a
# peer somebody actually runs a deploy or run script on. Adding a line has no such problem.
